Open Dental IT Support Guide: Multi-Location Replication, Sync, and Backup

Open Dental runs your schedule, your charts, and your billing. For one office, that is a server and a backup. For five offices, it is replication, sync, and a backup plan that has to work at every location. Here is how it all fits together.

Open Dental is open source practice management software, and it runs on a MySQL database. For a single office, the setup is straightforward: a server holds the database, workstations connect to it, and a backup copies the data off site. The software is flexible, the licensing is simple, and a small practice can run it well with basic IT support.

Multi-location is where the IT work gets real. Once a second office opens, staff need the same patients, schedules, and treatment plans from more than one building. That is a replication problem, a sync problem, and a backup problem, all at once. We set up Open Dental replication across five offices in a daisy chain, with the data syncing properly so every office saw the same data, and backups in place at each location. This guide is built on what that job taught us.

What Open Dental Replication Is

Replication copies database changes from one Open Dental server to another, automatically, as they happen. Each office runs its own Open Dental instance with its own MySQL database on its own server. When someone books an appointment at Office A, replication carries that change to Offices B, C, D, and E. When Office C posts a payment, the other offices see it too. Every office holds a full copy of the shared data.

That local copy is the point. If the internet link between two offices goes down, neither office stops working. Staff keep checking patients in and posting payments against the database in their own building. When the link comes back, the changes sync across. A single central server cannot do that. If it goes down, every office is stuck at once.

Replication is not cloud hosting, and it is not a VPN. Cloud hosting puts one database in a data center and every office connects to it. A VPN is just the secure tunnel between offices. Replication uses the tunnel, but the data lives at each office, not in one place.

How the Daisy-Chain Setup Works

In a daisy-chain setup, each office replicates to the next one in line. Office A sends its changes to Office B. Office B sends its own changes, plus the ones it received from A, on to Office C, and the chain runs through every office until the last one has the full picture. Changes flow in both directions, so an appointment made at the last office in the chain still reaches the first. The alternative is a hub-and-spoke layout, where every office replicates to one central server. A hub is simpler, but it becomes the single point everything depends on. A chain spreads that risk: losing a single link only isolates the offices past it until the link is fixed.

Here is what the setup actually involves:

The pieces in place before replication starts

  • A server at each office: Each location needs its own server running MySQL and Open Dental, reliable, on a UPS, and backed up. A workstation pulling double duty as a server is not a foundation for replication.
  • Site-to-site VPN tunnels: The offices connect over encrypted tunnels between their firewalls, not over the open internet. For on-prem offices we standardize on Sophos firewalls, and for cloud-based offices we use UniFi. The tunnel has to be always on.
  • The same Open Dental version everywhere: Version-for-version is a hard rule. An Open Dental update can change the database structure, and a server running a different version from the rest will stop replicating or, worse, replicate bad data. Upgrades are planned for all offices together.

Building the chain

  1. Pick the order of the offices in the chain. Geography usually decides it.
  2. Stand up the VPN tunnels and confirm each office can reach the next one. Each server needs a static internal address, since replication points at addresses and a server that moves breaks the chain.
  3. Install the same Open Dental version on every server, and confirm each office works on its own first. Replication is not a fix for a broken single-office setup.
  4. Configure MySQL replication office by office, starting at one end of the chain. Verify at each step that changes made at one office appear at the next, then test with real work: book an appointment at one end, check it shows at the other, post a payment, and check the same in the other direction.

Cutover work like this happens after hours. The practice keeps seeing patients during the day, the replication work happens at night, and the offices open the next morning with first-morning coverage in place. Zero patient downtime is the standard, not a stretch goal.

Keeping Instances in Sync Across Offices

Replication is not set-and-forget. When it breaks, it usually breaks quietly. The front desk notices hours later, when an appointment booked at another office is missing. The job is to catch sync problems before staff do.

What syncs

Replication carries the database: patient demographics, appointments, treatment plans, charting, billing, payments, and notes. Files outside the database need their own plan. Imaging files, scanned documents, and letter templates sit on disk at each office and do not move through MySQL replication. If offices share imaging, the image folders need a separate sync or a shared location every office can reach.

What to watch

  • Replication lag: Changes should appear at the next office within seconds. If lag grows to minutes, something is wrong: a slow link, a struggling server, or a backlog of changes.
  • Replication status: MySQL replication can stop on an error and sit stopped until someone restarts it. A daily check catches a stopped link the same day, not a week later.
  • Disk space: A full disk stops MySQL from writing, and a stopped database stops replication. Disk space gets monitored at every office, not just the main one.

What breaks

  • A VPN tunnel drops: The offices on either side keep working locally, and changes queue up until the tunnel is back. The fix is usually at the firewall or the internet connection, not in Open Dental.
  • A MySQL service stops: A reboot, a failed update, or a disk error can stop the database service. Open Dental will not open at that office until the service is running again.
  • One office gets upgraded alone: A version mismatch breaks replication between the upgraded office and the rest. The fix is to bring every office to the same version, then re-check sync.

Backup and Restore for Open Dental

Replication is not a backup. That is the most important line in this guide. If a record gets deleted at one office, replication deletes it everywhere. If ransomware encrypts the database at one office, replication can carry the damage along the chain. Replication protects against an office going offline. Backup protects against data loss. A practice needs both.

What a complete backup captures

  • The MySQL database: Patient records, appointments, treatment plans, billing, and notes all live here. A database dump or a MySQL-aware backup tool captures it.
  • Imaging files: X-rays and patient photos live in folders outside the database. They are often the largest part of the backup, and the part most often missed.
  • Scanned documents: Referral letters, insurance forms, and other scanned paperwork in the document folders.
  • Configuration: Open Dental settings, eConnector configuration, and custom templates. Small files, but rebuilding them after a loss costs hours.

How the backup should run

Each office backs up its own instance. Each office holds a full copy of the shared data, so a backup from any one office can restore the whole practice. But do not back up from only one office and assume the rest are covered. If that office's backup fails silently for a week, the practice has no backup at all. Back up at every office, keep a copy off site or in the cloud, and keep enough history to recover from a problem found days later. Backups should run on a schedule nobody has to remember, and someone should check they completed. Read our full dental data backup and recovery guide for backup types, retention, and recovery planning.

Testing restores

A backup that has never been restored is an assumption, not a plan. Test restores show whether the backup actually works, before the day it has to work.

  1. Restore the MySQL database to a test machine or a spare server, never to the live server.
  2. Open Open Dental against the restored database. Check that patients, appointments, and recent payments are there.
  3. Open a few images and documents to confirm the file backup restored alongside the database.
  4. Time the restore. Knowing it takes two hours matters when the practice is waiting to reopen.

Test restores should happen on a regular schedule, and right after any change to the backup setup. If the backup software changes, the server changes, or the imaging folder moves, test again at once.

⚠️ Never test a restore on your live server. Restore to a spare machine or a test environment. A restore test that overwrites the live database turns a drill into a real incident.

When a Practice Outgrows a Single Instance

Most practices start on a single Open Dental instance, and for a long time that is the right setup. Replication adds moving parts, and moving parts need monitoring. There is no reason to take that on before the practice needs it. But there are clear signs a single instance has run its course.

Signs it is time

  • A second office is opening: The clearest trigger. Staff at the new office need the same patient records and schedules as the first, and phoning across to check a schedule does not scale.
  • Staff keep calling another office to check the schedule: If the front desk regularly rings the other location to confirm an appointment or look up a patient, the offices already share data. They just do it by phone.
  • Patients move between offices: When patients see a hygienist at one location and a specialist at another, both offices need the same chart. A single instance with remote access can cover this for a while, but it gets fragile as volume grows.
  • One server is carrying too much: If every office connects to one slow server, the problem hits all of them at once. Replication spreads the load so each office leans on its own hardware.

Making the move

The move to replication is a project, not a settings change. It starts with a plan: the order of the offices in the chain, the VPN tunnels between them, the server at each location, and a version check so every office runs the same Open Dental release. Data gets staged ahead of time where possible, and the cutover happens after hours so the practice never loses a patient day. The first morning after cutover gets on-site or remote coverage, so any sync issue is caught before the schedule fills up.

For a practice weighing the move, the question is whether the offices already share patients, staff, and schedules in practice. If they do, replication turns a workaround into infrastructure. If they operate as separate practices that happen to share an owner, separate instances with good backups may still be the right call.
